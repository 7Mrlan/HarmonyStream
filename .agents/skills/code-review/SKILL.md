# Code Review（Claudio 项目）

## 审查姿态

- **问题先行**：先列 findings，按严重程度排序；整体总结只能放在问题之后。
- **实事求是**：没有真实问题时，明确说“未发现需要修改的问题”，不要为了凑数制造建议。
- **可定位**：每个问题必须包含文件、函数或行号，并说明证据、影响和修复方向。
- **可追溯**：结论必须来自代码、diff、Spec、测试输出或项目规则，不用“通常来说”替代证据。
- **范围克制**：只审查用户指定范围或本轮改动，不把无关脏工作区改动混进结论。

## 必查上下文

1. 先看 `git status --short`，区分本轮改动、用户已有改动和未跟踪文件。
2. 查看相关 `git diff`、调用链和测试文件；需要搜索时优先用 `rg`。
3. 中等及以上任务必须对照 `tasks/spec.md` 与 `tasks/todo.md`，Spec 与代码冲突时以 Spec 为准。
4. React Native / Expo 代码同时套用项目 skill：图片优先 `expo-image`，动画优先 Reanimated / Skia，公共 props 用 TypeScript 类型。
5. 服务端电台、音乐解析、TTS、队列和 `/api/chat` / `/api/now` 相关改动必须检查是否需要 `pnpm test:full`。

## 审查维度

- **功能正确性**：主流程是否闭环，边界条件、错误分支、竞态和状态同步是否可靠。
- **架构边界**：是否违反已有模块职责，是否绕过封装组件、API client、provider chain 或 Spec 决策。
- **测试与验证**：是否覆盖新增行为、回归场景和失败分支；验证命令是否与 AGENTS 规则匹配。
- **性能与资源**：是否引入高频重渲染、泄漏、无清理副作用、阻塞 I/O、无界缓存或 N+1 请求。
- **安全与数据**：是否泄露密钥、扩大外部输入执行面、引入注入风险或破坏本地优先约束。
- **可维护性**：命名、类型、注释和复用是否足够清晰；风格建议只有收益明确时才提出。

## 严重程度

- **致命**：会导致数据丢失、安全事故、主流程不可用或构建完全失败。
- **严重**：会造成明显功能回归、线上崩溃、状态错乱或关键验收失败。
- **一般**：边界场景错误、测试缺口、性能退化或维护风险已经可定位。
- **建议**：不阻塞合并，但收益明确且改动很小。

## 输出格式

有问题时：

```text
Findings
- [严重] path/to/file.ts:123 `functionName`：问题标题
  证据：引用代码行为、diff 或测试输出。
  影响：说明真实用户或系统会怎样受影响。
  建议：给出最小修复方向。

Open Questions
- 需要用户或 Spec 确认的点。

Verification
- 已运行 / 未运行的验证，以及未覆盖风险。

Summary
- 简短总结整体质量和可保留的优秀实践。
```

无问题时：

```text
未发现需要修改的问题。
Verification
- 已检查的范围和已运行 / 未运行的验证。
Residual Risk
- 仍未覆盖或依赖人工验收的部分。
```

## 禁止事项

- 禁止先给大段正向总结再列问题。
- 禁止提出无法定位、无法解释影响的泛泛建议。
- 禁止把个人风格偏好包装成缺陷。
- 禁止在纯 review 请求中直接改代码；只有用户明确要求“审查并修复”时才进入最小改动。
